# testes-sync

Testes do sync com **duas pontas**: o motor de verdade do Corona Vendas (a mesma montagem do app, `apps/seller-app/src/main/montagem.ts`, com o banco SQLCipher de verdade) rodando em Node contra a API de verdade e um PostgreSQL descartável, com vários computadores e uma rede ruim com semente (tarefa 5.12; ADR-0013, item 20).

## Como rodar

Precisa do Docker aberto e das portas **5498** (PostgreSQL) e **8098** (API) livres. Nunca usa o banco de desenvolvimento (5432) nem o do e2e (5499).

```bash
npm test -w @corona/testes-sync                    # só os testes sem API (proxy, varredura): segundos
npm run test:duas-pontas -w @corona/testes-sync    # cenários e estresse curto (1 min): cerca de 6 a 8 min
CORONA_SYNC_DURACAO=PT10M npm run estresse -w @corona/testes-sync   # só o estresse, longo
```

| Variável              | Para quê                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `CORONA_SYNC_SEMENTE` | Repete uma falha: a semente sai no log de cada arquivo ("Duas pontas (...): semente=..."). Sem ela, vale a hora.          |
| `CORONA_SYNC_DURACAO` | Duração do estresse (ISO-8601: `PT1M`, `PT10M`). Padrão `PT1M`.                                                           |
| `CORONA_SYNC_JAR`     | Pula a compilação da API e usa este jar (caminho absoluto ou relativo à pasta `testes-sync`). Use um jar do código atual. |

O `globalSetup` (`ambiente/preparar.ts`) derruba e sobe o PostgreSQL (`ambiente/docker-compose.yml`, projeto `corona-sync`, sem volume), compila a API (`mvnw -DskipTests package`), sobe o jar e espera a saúde; no fim, desmonta tudo. O log da API fica em `testes-sync/resultados/api.log` (no CI, vira artefato quando falha).

## Como funciona

- `src/aparelho.ts`: um "computador do vendedor". Pasta temporária própria, cofre de teste (AES-GCM com chave na memória, no lugar do DPAPI), o `fetch` do Node apontado para **um proxy só dele** e um relógio de teste (hora real mais um deslocamento; as esperas do motor andam 10 vezes mais rápido). O teste fala com o app pelos mesmos pedidos que a tela manda pela ponte (conferidos pela mesma validação) e só **lê** o banco local.
- `src/dona.ts`: a dona pela API de verdade, sem proxy (vendedor, peça, estoque, foto, maleta, preço, códigos, trocar e bloquear computador, quarentena, envios com problema, conciliação). Cada maleta cria uma semana "bem no futuro": o número começa entre 1 e 90000 conforme o segundo do relógio e nunca passa do limite da API (100000); o `dona.test.ts` confere isso para qualquer hora, lendo o limite do próprio `SemanasDaDonaController` (issue #130).
- `src/proxy-de-rede-ruim.ts`: atraso, queda antes, **corte depois de o servidor gravar**, corte no meio da resposta, 502, banda; roteiro geral, **roteiro por caminho** ("o 1º push corta depois de gravar") ou sorteio com semente; troca de cabeçalho (a versão do app, para imitar a dona subindo a versão mínima); observador de toda resposta.
- `src/oraculo.ts`: o que é de cada vendedor, calculado à parte em SQL (a mesma regra do `CenarioDeSync.oraculo` do backend), lido pelo `psql` do contêiner (só leitura).
- `src/afirmacoes.ts`: a afirmação final, a mesma para todo cenário e para o estresse: cópia local igual ao oráculo (toda linha, versão e lápide; nenhuma provisória), nada privado de outro vendedor, nenhum marcador proibido (`scripts/marcadores-proibidos.json` mais custo e fornecedor) em **nenhuma** resposta que passou pela rede, colunas locais só as da lista do pull, cada operação do livro com destino no servidor (aceita uma vez, recusada ou em conflito nos "envios com problema", ou em quarentena) e a conciliação "estoque + maletas" fechando. Antes de comparar, liga a internet de **todos** os computadores vivos e dá voltas (cada um envia e recebe até zerar) até uma volta inteira em que o retrato do servidor (as 15 tabelas que vão ao vendedor) não mudou, no máximo 5; o log diz quantas voltas foram ("Afirmação final: N voltas"). Assim, todo computador recebe depois do último envio de qualquer outro (issue #130). Na falha, imprime a semente, o histórico de cada proxy (com a hora de cada pedido), o registro de cada app e, para cada linha que faltou, o `sync_xid`/`sync_seq` dela, o envio no `sync_log` e o cursor de cada computador.

### A máquina do tempo (só para a devolução fora do prazo)

A API corrige e limita toda hora que vem do computador, então toda venda do teste é "de hoje" para o servidor e ele nunca acharia nada fora do prazo. `src/maquina-do-tempo.ts` **envelhece uma venda já gravada** no banco descartável: só a data (`vendas.vendida_em`), numa transação que desliga apenas o gatilho de conteúdo da venda e o liga de novo (DDL do PostgreSQL é transacional: ninguém vê o gatilho desligado e um erro desfaz tudo). Os outros gatilhos seguem ligados, então a data nova chega ao computador pelo recebimento. É o **único** ponto do `testes-sync` que grava no banco do servidor, e só nessa coluna; nunca toca o banco de desenvolvimento nem o código da API. Perto da meia-noite de Brasília (menos de 10 minutos) o teste espera a virada, nunca pula. Os prazos vêm da rota de garantia da dona (nada de 7 e 30 escritos no teste).

O relógio do computador **atrasado** nasce com o computador (`deslocamentoMs` ao ligar): depois de um contato com o servidor, um relógio que anda para trás é "relógio mexido" e bloqueia a gravação (ADR-0013, item 12). O adiantado pode ser posto a qualquer hora.

## Como repetir uma falha

1. Pegue a semente no log (`Duas pontas (...): semente=...`) ou no relatório da falha.
2. Rode só aquele arquivo com ela: `CORONA_SYNC_SEMENTE=<semente> npm run test:duas-pontas -w @corona/testes-sync -- src/cenarios/<arquivo>`.
3. A semente repete as decisões da rede de cada pedido e o roteiro do estresse; a hora exata em que cada pedido sai não se repete (rede e API de verdade), por isso o estresse só afirma o estado final.
